# Slide-deck build sources

`build_reveal.py` and `build_deck.py` are **generic renderers**, shared across every
`talk_content.py`-style deck in this repo (not just the RIT talk) -- each deck keeps its
own content module (a Python list `SLIDES` of dicts) next to its own `slides/` output and
`.pptx`, and calls into these two scripts by path:

```
python3 scripts/build_reveal.py path/to/talk_content.py   # -> <that dir>/slides/index.html
python3 scripts/build_deck.py   path/to/talk_content.py [out.pptx]   # -> out.pptx (or <that dir>/rit-talk.pptx)
```

Called with **no argument**, both default to `talk_content.py` next to the script itself
(this directory's RIT talk), so the original one-word invocations below still work
unchanged. The Discrete Planning lecture deck is a second example of this pattern: its
content lives in `chapters/01-1901-discrete-planning/deck/talk_content.py`, and
`make chapters/01-1901-discrete-planning/exports/DiscretePlanning.pptx` builds it (see
the repo's top-level `Makefile`).

Either way, `talk_content.py` is the only place slide content and speaker notes live;
both renderers read it and stay in sync whenever you rerun their build script.

- **`slides/index.html`** (reveal.js) — the primary deck. Plain HTML/CSS/JS, real
  `<video controls>` elements — no LibreOffice animation-timing fights, no imported
  jQuery-era custom JS. On the video-demos slide, each clip is revealed and played one
  at a time on keypress (see "Video playback" below). Speaker notes built in (press
  `s`). Generated by `build_reveal.py`.
- **`rit-vision-talk.odp`** (LibreOffice/PowerPoint) — kept around as a fallback /
  offline-file-you-can-email option. Generated by `build_deck.py` + `soffice`.

## Files

- `talk_content.py` — **single source of truth.** A Python list `SLIDES` of dicts; each
  dict is one slide: `type`, on-slide text (`title`/`bullets`/etc.), and `notes`
  (the speaker-notes narration for that slide). Edit this file to change content —
  both renderers pick it up automatically.
- `build_reveal.py` — reads `talk_content.py` and renders `../slides/index.html`
  (layout/styling for each `type` lives here as HTML+CSS — edit this to change how a
  slide *type* looks).
- `build_deck.py` — reads `talk_content.py` and renders `rit-talk.pptx` (layout/styling
  logic for each `type` lives here — edit this if you want to change the ODP/PowerPoint
  version's look).
- `gen_notes.py` — reads `talk_content.py` and writes `../speaker-notes.md` (a plain
  printable script, independent of either renderer).
- `media/` — all images used in the deck (extracted figures, downloaded YouTube
  thumbnails, logos, headshots).
- `media/videos/` — the actual video files (H.264/AAC mp4, re-encoded from YouTube via
  `yt-dlp` + `ffmpeg` — see "Videos" below). Referenced directly by both renderers.
- `build.sh` — runs the ODP pipeline: `./build.sh` rebuilds the pptx, the notes, and
  `../rit-vision-talk.odp`. `./build.sh --preview` also renders PNG slide previews into
  `build/preview/`.
- `../slides/vendor/reveal/` — vendored reveal.js 6 (core JS/CSS + the notes plugin),
  pulled once via `npm pack reveal.js`. No npm/node needed at presentation time — it's
  plain static files.
- `../serve.sh` — starts `python3 -m http.server` **from the project root** and prints
  the URL. Run this (not a server rooted inside `slides/`) — see "Serving" below.

## To edit content or notes

Edit the relevant slide dict in `talk_content.py`, then:

```
python3 build_reveal.py   # regenerates slides/index.html
./build.sh                 # regenerates the ODP + speaker-notes.md (optional)
```

## Serving the reveal.js deck

`slides/index.html` references images/video as `../build/media/...` — paths that live
*outside* `slides/`. Serve from the **project root** so both `/slides/...` and
`/build/media/...` resolve under the same server:

```
../serve.sh          # from build/, or just run ./serve.sh from the project root
```

Then open `http://localhost:8000/slides/index.html`. (A server rooted at `slides/`
itself will 404 on every image/video — always serve from one level up.)

## To add a slide

Add a new `dict(...)` to the `SLIDES` list in `talk_content.py` at the position you want
it to appear, with a `type` matching one of the branches in **both** `build_reveal.py`
and `build_deck.py` (`title`, `bio`, `section`, `content`, `content_img`, `image_full`,
`code`, `gallery`, `demo`, `pillars`, `triad`, `pipeline`, `videos`, `team`, `pubs`,
`end`). Reuse an existing type where possible — most content slides are just `content`
(bulleted) or `content_img` (bullets + one image).

Three of these were added for the Discrete Planning deck and are generally useful:
- `code` — a monospace code snippet (`code`, plus optional `bullets`, `img`,
  `colab_note`). Keep snippets short and high-tutorial-value; point long/utility code at
  a notebook or Colab link via `colab_note` (supports `[label](url)` markdown links)
  instead of pasting it in.
- `gallery` — a row of 2-4 captioned images (`images=[(path, caption), ...]`); for a
  short sequence of figures (e.g. heapify -> insert -> extract-max) that don't each need
  a full slide.
- `demo` — a highlighted interstitial marking "switch from slides to the live
  notebook/Colab" (`bullets`, `colab_url`, optional `img`). Use these sparingly, at the
  points where a live run genuinely adds more than a static slide would.

Any bullet list (`bullets`/`pubs`) accepts inline `[label](url)` markdown links, rendered
as real hyperlinks in both the reveal.js `<a>` and the pptx (as a real
`run.hyperlink.address`, not just visible text).

**Code-block whitespace:** PowerPoint/LibreOffice are both free to collapse leading and
repeated spaces inside a plain text run (no `xml:space="preserve"` by default in
python-pptx), which silently destroys Python indentation in the ODP. `add_code_block` in
`build_deck.py` works around this by swapping every space for a non-breaking space
(` `, never collapsed) and setting `xml:space="preserve"` on the run as a second
safeguard -- if you add another place that renders literal/indented text into a pptx
textbox, reuse `add_code_block` or apply the same fix rather than a plain `add_text`.

## To add a new slide *type* (new layout)

Add a new `if typ == "your_type":` branch in `build_reveal.py` (and, if you also want it
in the ODP, a matching `elif typ == "your_type":` in `build_deck.py` — search for
`elif typ ==` there to see the existing ones as templates), then use
`type="your_type"` in `talk_content.py`.

## Video playback in reveal.js: one at a time, on keypress

`build_reveal.py`'s `"videos"` branch marks each `.video-card` `class="fragment"` and
each `<video>` `data-autoplay`. Reveal.js core (vendored, unmodified) already:
- skips autoplay for a video inside a `.fragment` until that fragment is actually
  shown (`js/controllers/slidecontent.js`, `startEmbeddedContent`), and
- pauses it again when the fragment is hidden, or when you leave the slide
  (`js/controllers/fragments.js`, `stopEmbeddedContent`).

That's the whole "reveal + autoplay + pause-on-leave" behavior — no custom code
needed, unlike `oldtalks/safe-autonomous-nav-talk-sep2022/index.js`'s ~500-line
version of this (which also carries a lot of unrelated SVG/footnote/chapter-progress
machinery from that talk).

The one thing reveal.js doesn't do on its own is enforce "only one plays at a time" —
by default, fragments accumulate (video 2 appearing doesn't stop video 1). The inline
script at the bottom of `build_reveal.py`'s `HTML_TEMPLATE` adds two small `Reveal.on(...)`
handlers for that:
- `'fragmentshown'` — pause every video except the one just revealed (forward stepping).
- `'slidechanged'` — handles stepping *backward into* this slide from the next one: reveal.js
  re-autoplays every already-visible fragment's video in one batch (not per-fragment), so this
  keeps only the last-shown one playing. It's deferred with `setTimeout(0)` because reveal.js
  fires `'slidechanged'` *before* its own `startEmbeddedContent(currentSlide)` call in this
  version — an immediate `pause()` gets clobbered a moment later otherwise.

This was verified by driving headless Chromium over the DevTools Protocol (`Reveal.next()`/
`Reveal.prev()` + reading each `<video>`'s `paused`/`currentTime`), not just eyeballed — all
five steps (each of the 3 videos in turn, leaving the slide, and stepping back into it) behave
correctly. If you add a fourth video or a second video-fragment slide, this logic doesn't need
touching — it works off the DOM, not video count.

## Videos (the `videos` slide type)

Video shapes are real embedded media (`slide.shapes.add_movie(...)` in `build_deck.py`),
not hyperlinked thumbnails — the deck is self-contained and plays offline. Each entry in
a slide's `videos` list is a dict: `thumb` (poster-frame image), `caption`, `url` (source,
kept as an on-slide credit link), and `video` (the local mp4 to embed). This is the ODP
renderer's video handling — separate from the reveal.js behavior described above.

To add/replace a video:

```
yt-dlp --no-warnings -o "name.%(ext)s" \
  -f "bestvideo[height<=480][vcodec^=avc1]+bestaudio[ext=m4a]/best[height<=480][vcodec^=avc1]/best[vcodec^=avc1]" \
  --merge-output-format mp4 "<youtube-url>"
```

Request `vcodec^=avc1` (H.264) explicitly — YouTube's default best-quality streams are
often AV1, which PowerPoint/Impress frequently can't play. If a download still comes back
AV1 (check with `ffprobe -show_entries stream=codec_name file.mp4`), re-encode:

```
ffmpeg -i in.mp4 -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 23 -preset medium \
  -c:a aac -b:a 128k -movflags +faststart out.mp4
```

Put the result in `media/videos/`, grab a poster-frame thumbnail (e.g.
`https://img.youtube.com/vi/<VIDEO_ID>/hqdefault.jpg`), and point a `videos=[dict(...)]`
entry at both.

## Requirements

- `build_reveal.py`: just Python 3 (stdlib only). The generated `slides/index.html` is
  static — no npm/node/build step needed to present it, and the vendored reveal.js
  under `slides/vendor/reveal/` doesn't need re-fetching unless you want a newer
  version (it was pulled once via `npm pack reveal.js`).
- `build_deck.py` / `build.sh`: Python 3 with `python-pptx` and `Pillow`, plus `soffice`
  (LibreOffice) and `pdftoppm` (poppler-utils) on PATH for the ODP/preview conversion.
- `yt-dlp` and `ffmpeg` are only needed if you're adding/replacing videos — use a
  current `yt-dlp` (`pip install --user --upgrade yt-dlp`); old distro-packaged versions
  can fail to extract YouTube formats at all.
